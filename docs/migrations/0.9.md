# Migrating to 0.9

Purpose definitions now use `on` for their target constraint:

```json
{
  "version": 1,
  "scopes": {
    "dialog": {
      "purposes": {
        "trigger": {
          "description": "Opens the dialog.",
          "on": { "element": "button" },
          "layer": "contract",
          "declaration": "required"
        }
      }
    }
  }
}
```

Replace a purpose's former `role` key with `on`. Its value is unchanged:
`element` restricts the actual HTML element; `aria` restricts explicit or
statically provable implicit ARIA semantics. Omit `on` for an unrestricted
purpose. This constraint never assigns semantics or behavior.

Existing definitions using `role` remain valid. Do not specify both keys on
one purpose, even when their values match. Sources using different spellings
compose identically when their definitions otherwise agree. Normalized registry
records retain the existing `role` field for API compatibility.

Markup, base classes, variants, diagnostic IDs, ownership, and the defaults
`layer: "implementation"` and `declaration: "optional"` do not change. A
role's meaning may include a use, but declaring a role does not implicitly
register a separate same-named purpose.

This release does not add behavioral requirements or test mappings to the CSS
schema and does not change the Nagi UI definition format.
