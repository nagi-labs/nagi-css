# Migrating to Nagi CSS 0.4

Nagi CSS 0.4 makes variant necessity mechanically reviewable. Upgrade all
three Nagi CSS packages together because the core analysis and ESLint rule
metadata share one version.

## Non-STN variants require a peer

`variant-requires-peer` is an error. A non-STN variant is useful only when the
same base identity occurs at least twice in the component:

```html
<button class="button -cancel">Cancel</button>
<button class="button -save">Save</button>
```

Remove a variant from a base that occurs once, and update its selector in the
same change:

```diff
- <article class="article -slide">...</article>
+ <article class="article">...</article>

- > .article.-slide { ... }
+ > .article { ... }
```

The peer may be elsewhere in the same component; it need not be a sibling or
carry another variant. Runtime repetitions from one `v-for`/`each` template
branch still count as one authored occurrence, so a common variant on every
item is redundant.

The rule has no autofix. Template classes and all matching selectors must be
changed together.

## STN variants remain role names

STN bases describe structural depth rather than local role, so they are exempt
from `variant-requires-peer`. A lone `unit -viewport` remains valid.

When multiple static sibling branches use the same STN tier, however, each
branch should have a unique role variant:

```html
<div class="unit -announcements">...</div>
<div class="unit -stack">...</div>
```

`stn-peer-variant` reports indistinguishable sibling STN branches as a warning.
It excludes repeated collection branches and mutually exclusive conditional
branches because those represent instances or alternatives of one logical
role.

## What does not count as a peer

Peer identity comes from the Nagi CSS base class. Ancestor paths, `data-part`,
accessible names, and ARIA ID relationships do not create another base
occurrence.
