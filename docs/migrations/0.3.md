# Migrating to Nagi CSS 0.3

Nagi CSS 0.3 changes lint behavior and adds configuration used by alternate
component implementations. Upgrade all three Nagi CSS packages together when a
project depends on more than one of them.

## Paragraph and short-text identities

A prose paragraph now self-maps:

```html
<p class="p">A complete prose paragraph.</p>
```

`text` is anatomy for a short UI label or textual run on `div` or `span`:

```html
<span class="text">Online</span>
```

Change `<p class="text">` to `<p class="p">`. If the content is not actually a
paragraph, change the element as well; deciding whether content is prose remains
an HTML-authoring review rather than a CSS lint conclusion.

## Role-first identity

An identifying ARIA role on `div` or `span` now takes precedence over anatomy or
STN. For example, `<div role="status">` uses `class="status"`. Generic,
presentation, and none roles do not provide identity. Do not add a role only to
obtain a class name.

The role correction is safely fixable when the existing class is an anatomy or
STN fallback and no competing base identity exists.

## Static variants

A static variant may express a local distinction even when the component has no
same-base peer. This permits `class="section -summary"` when `section` is the
derived base and `summary` is stable local meaning. Variants remain unsuitable
for runtime state; use native, ARIA, or `data-*` attributes for that.

## Motion and render proxies

Use `intrinsicComponents` when a component renders one known HTML element and
should participate in the same identity and ownership analysis:

```js
intrinsicComponents: {
  "motion.div": "div",
  "motion.section": "section",
}
```

Use `transparentComponents` for control-only wrappers that add no rendered DOM
level:

```js
transparentComponents: ["AnimatePresence"]
```

These mappings describe rendered structure; they are not broad exceptions. Add
only components whose output contract is known.

If a repository contains both package consumers and owned replacement sources,
give them separate ESLint config entries. Apply the package component-boundary
map only to consumer templates. An owned replacement uses its own surface prefix
and must not be registered as an opaque `componentClasses` boundary.

## Layout wrapper advisory

`layout-only-wrapper` warns when a sole-child `div` or `span` appears to exist
only to establish flex or grid layout around one child branch. It is a review
candidate, not a proven violation, and therefore warns by default. Keep the
wrapper when it owns a meaningful layout boundary.

## Declaration backend

`declarationMode` defaults to `"plain"`, which provides complete visibility into
component declarations. Existing plain-CSS projects need no configuration.

`"tailwind-apply"` is an experimental compatibility backend in 0.3.x. It keeps
template vocabulary and selector checks but delegates utility expansion and some
declaration guarantees to Tailwind. Do not adopt it as a stable portability
contract yet.

## Suggested upgrade sequence

1. Upgrade the packages together.
2. Run the project's normal ESLint command without `--fix` and review the new
   rule families.
3. Run `--fix` only on a reviewed scope for unambiguous identity corrections.
4. Review paragraph semantics and layout-wrapper warnings manually.
5. Keep the final CI configuration at error severity except for intentional
   advisory or unverifiable cases.
